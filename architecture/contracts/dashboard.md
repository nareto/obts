# Dashboard Contract

## Application Shell

The dashboard is a compact authenticated Svelte/Vite/TypeScript SPA served by the Fastify server. It is an operational application, not a marketing site or decorative analytics dashboard.

Primary navigation is Overview, Devices, Conflicts, History, Maintenance, and Settings. Status refreshes retain the selected vault for the authenticated user, but any remembered vault ID is revalidated against current ownership before use. The content header shows page title, selected vault/status context, unobtrusive refresh state, and practical primary/secondary actions without decorative controls.

Desktop uses a persistent 240px navigation rail with icon+label navigation and a clear active state, compact tables, and a scrollable content region. Below the responsive breakpoint the rail becomes a touch-sized drawer with a backdrop, close/Escape behavior, focus return/trapping, background scroll suppression, and no interaction with inert content. Technical identifiers are monospace, truncated by default, copyable, and never the primary human explanation.

## Request Ownership

Changing vault clears its review/history content and scoped actions before loading the next vault. Account transitions additionally clear account-scoped presentation state. Dashboard snapshots, conflict reviews, history responses, and vault/device mutation completions must not repopulate another account or vault. A status snapshot requested after a review request invalidates that pending review; a snapshot requested before it never discards it. A conflict review refresh is a manual refresh, so live updates it causes wait behind it as a trailing refresh. The server's `stale` flag and a changed reviewed main decide whether a conflict changed; a main advance alone does not. Changed or unavailable conflicts preserve an open draft only as non-submittable stale content. Successful renames supersede older dashboard snapshots. Polling does not supersede an active manual refresh or reset an unchanged conflict draft.

Sign-out clears the local view immediately and blocks another sign-in until its request finishes. A failed server sign-out is reported as incomplete and offers retry; the UI must not imply that the remote session was terminated successfully.

## Status Vocabulary

Statuses combine text and icon; color is never the sole signal.

- **Success:** Synced, healthy, complete.
- **Active/information:** Uploading, Applying, Checking, Verifying contents, Preparing upload, Merging, Server retrying, Repairing baseline, Finishing update.
- **Warning:** Out of sync, Ahead, Behind, Offline, Status unknown, Stale review.
- **Danger:** Conflict resolution needed, Out of sync — file exceeds upload limit (blob), Out of sync — upload limit exceeded (other Git object), Out of sync — local recovery required, Blocked, Needs recovery, Integrity failure.

### OBTS-DASH-STATUS-001: Truthful Local Sync Failure Presentation

“Unsafe local state” is not an active user-facing status, including for persisted older reports. A pending upload, retry or deferred local edit is out of sync, not a conflict or evidence of corruption. “Conflict resolution needed” is reserved for an actual unresolved server conflict. Recovery required means automatic safe continuation could not be established and must identify the reason and supported next action; unknown failures remain neutral and show a bounded safe code without promising that all work was uploaded or independently preserved. Transfer size failures show the actual limit and locally available object size, type, version, and path when known; historical objects without a current path are identified honestly. Oversized-object paths, object OIDs, exact object sizes, content and arbitrary exception messages stay local, never in shared status or diagnostic telemetry. Commit-reference OIDs already carried as device sync cursors (`local_main`, `local_head`) remain available in authenticated dashboard details; they must not be confused with the oversized-object OID. Legacy error codes remain interpretable and old status labels are normalized at presentation boundaries.

Long-running local work remains an active truthful operation with elapsed/detail information. The shared dashboard displays coarse progress (10% buckets) rather than exact client-reported counts; exact progress stays local. It does not become Offline solely because local processing took time. Device convergence comes from fresh server/client reports, not browser-side aging guesses.

### OBTS-DASH-SET-001: Vault Sync Settings

Selected-vault Settings groups shared sync exclusions and metadata conflict rules under **Sync**. The exclusions editor previews the existing vault-root `.gitignore` bytes with the same Git matcher as sync, names newly excluded canonical files/directories, and saves through a stale-main and stale-policy protected server operation. It clearly explains that this is versioned `.gitignore` content consumed by clients, while direct file edits remain ordinary sync proposals. Newly excluded content remains in each device's visible vault as local-only; accepted history remains protected and unignore does not restore old content automatically. The plugin shows the effective shared file read-only and links to server Settings; it may still show a pre-pairing local copy, and reports offline/loading/error state truthfully.

Metadata conflict rules are explicit per-vault frontmatter field names and the supported `Latest timestamp` strategy. UI text states the supported timestamp format: explicit-offset ISO-8601, up to nine fractional digits; unzoned, malformed, invalid, or higher-precision values fall back to normal conflict review. Rule changes affect future integrations only. Settings drafts and previews are scoped to the selected account, vault, current main, and policy identity; switching scope invalidates them. Failed saves retain the draft and explain stale reviews so the user can reload and preview again.

### OBTS-DASH-NAME-001: File Name Repair For Restricted Devices

The dashboard summary reports the number of canonical paths on current main that are unrepresentable under `OBTS-SYNC-NAME-001`, the restricted platforms that rule covers, and which paired devices run on them. When current main cannot be read, the summary omits this projection instead of failing the dashboard read; health already reports the inconsistency. When the count is non-zero, Overview attention links to a Devices-page repair panel that explains which devices cannot store those names and which are currently blocked by them. Preview is owner-scoped and read-only. It lists every proposed rename with its reason (reserved characters or case-only collision) and every note whose links will change.

The mapping is deterministic. `:` and `|` become ` -`, `"` becomes `'`, `\` becomes `-`, and the remaining reserved and control characters are removed. Whitespace is collapsed and trimmed, and an empty name becomes `Untitled`. Case-variant directory spellings are unified onto the lexicographically first spelling. Remaining collisions get ` (2)`, ` (3)` suffixes, and no final path may collide case-insensitively with another. Link rewriting covers Obsidian wikilinks and embeds (path, basename, heading and alias forms), Markdown links and embeds (relative or vault-absolute, percent-encoded or angle-bracketed) outside fenced and inline code, and Canvas file nodes. All other bytes are preserved exactly.

The review fingerprint binds the current main, the candidate tree, and the complete rename and link outcome. Apply recomputes the preview under the vault mutation lock, rejects any changed outcome as stale, and commits one server-authored main commit through the ordinary durable ref-transition operation (`OBTS-PER-OP-001`), recording explicit-directory renames as directory intents. A candidate whose new paths the root policy would exclude fails closed. Renamed files reach devices as ordinary deletions and creations. A device with unsynced edits to an affected note integrates them through normal merge and conflict review.

## Overview And Devices

Overview summarizes synchronization, unresolved conflicts, paired devices, readiness, attention items, recent activity, maintenance, and backup contract state. Its four summaries are a compact adaptive status strip, followed by independently sized Devices/Attention and Activity/Maintenance columns; informational content remains available without stretched empty panels. Devices are shown in a concise operational table with name/status as the primary explanation, plugin version versus server recommendation, human relative times with exact accessible timestamps, ahead/behind state, and touch-sized actions. Expandable technical details retain identifiers, cursors, local detail, and exact report timestamps. A compact Overview table variant may omit secondary columns, while the Devices page keeps the full operational view. Status always combines readable text and icon; plugin mismatch is understandable without color alone.

Device last-seen is a coalesced liveness observation with up to 60-second granularity, not a per-request log; this precision does not replace fresh server/client reports as the authority for convergence. Every authenticated request revalidates session existence, revocation, account authority and absolute/idle expiry from authoritative metadata. A liveness write may be coalesced for at most one minute per session; it never extends absolute expiry. Stream heartbeats do not count as user activity or extend idle expiry.

### OBTS-DASH-HEALTH-001: Fresh, Observational Dashboard Health

Dashboard and maintenance health displays use the latest completed deep readiness sample; they do not trigger or wait for per-request Git fsck. A single server-owned sampler runs initially outside dashboard requests and periodically (five minutes by default); explicit readiness probes still request a fresh check and share the in-flight sample. Health projections expose `checked_at`, `checking`, `stale`, and a normative additive `state` ∈ {`verified`, `not_ready`, `stale`, `pending`, `failed`}: `verified` = a non-stale completed sample reported ready and no current failure exists; `not_ready` = a completed sample or current authoritative state reports a failure; `stale` = no sample completed within twice the sampling interval; `pending` = no sample has completed since start; `failed` = the newest sample could not complete. `status` is `ready` only for `verified`; every other state is `not_ready` with all unverified checks false. While a sample is `checking`, the previous completed verdict stays projected (not stale) for up to the interval plus a slack window, so a slow re-sample never flips a healthy server to `not_ready`. Missing, stale, failed, lifecycle-unavailable or durability-uncertain observations are never presented as verified healthy. When a completed sample's verdict (status, state, checks, detail) differs from the previous one, the server pushes `invalidate {account: true, vault_ids: []}` to every open dashboard stream; health is server-wide, so this carries no per-owner data. Current lifecycle, metadata durability, and selected-vault blocking conditions override cached results. The cache is observational only and never authorizes synchronization or mutation.

Device revocation is a danger action with explicit confirmation. Rename changes server display metadata only and does not rename a physical vault folder. Revoked devices are excluded from ordinary paired-device counts/status summaries but remain inspectable in a discoverable Revoked view. Permanent removal is a separate owner-session and CSRF-protected action for already-revoked devices only. Its dialog captures the immutable account/vault/device target and requires `DELETE <device_id>`; opting to discard unmerged work additionally requires `DELETE <device_id> AND DISCARD UNMERGED WORK` and an explicit warning. It does not request recent authentication. Conflicts and unsettled/prepared operations block removal with actionable safe reasons. Missing/unknown ref ownership or residue blocks rather than guessing. Successful removal is reported only after all attributable records/material are removed or durably accounted for; retryable work remains visible in Revoked, and failed removal attempts remain visible in Revoked with their safe failure code.

### Dashboard Routes And Refresh Ownership

Routes are `/dashboard/vaults/:vaultId/{overview|devices|conflicts|history|maintenance|settings}`, `/dashboard/vaults/:vaultId/conflicts/:conflictId`, and account `/dashboard/settings`. The URL is navigation authority and survives direct opening, reload, and Back/Forward; encoded segments are parsed safely. `/` and `/dashboard` canonicalize to the first accessible vault overview. Legacy `?vault=<owned-id>` redirects to that vault's Settings. Unknown or inaccessible IDs render a visible safe not-found state and never silently select another vault for a consequential action. `/connect/:connectionId` onboarding remains unchanged.

Changing route uses the existing account/vault generation and scope-clearing guards. Background refresh preserves same-scope conflict/settings drafts; changed or unavailable conflicts remain visible but stale and non-submittable. Dirty consequential drafts are keyed and preserved or require deliberate discard before navigation, including browser history navigation. Dashboard invalidation is coalesced, but an event received during an in-flight manual or automatic refresh creates a trailing refresh obligation; it cannot cancel manual ownership or allow stale responses to overwrite a newer scope. Revoked-device dialogs clear when account, vault, or device generation changes.

## Conflict Workbench

The conflict queue identifies path, named device, type, created time, status, and action. The review workbench provides affected-file navigation, provenance, server revision, named-device revision, rendered/source comparison, structural Base/Server/Device paths, directory outcomes, and available resolutions.

Every diff and resolution choice must identify **Server main** and **Device: <display name>** persistently and accessibly. Meaning cannot depend on red/green color, `+`/`-` familiarity, or an earlier caption. A compact source legend stays visible while the comparison scrolls: `− Server main` uses the server/red background, `+ Device: <display name>` uses the device/green background, and the legend states that colors identify versions rather than the changes the user chose to keep. Line numbers and existing coloring are preserved. Keep-both ordering and manually prefilled content provenance are explicit.

Content conflicts are decided per file. Each file carries its own choice: server, device, line by line, keep both copies, insert both blocks, or edited final content. Paths that a structural review group or an overlapping file/directory path links form one decision unit and share a single choice; a renamed note's old and new paths are decided together. Line by line and edited content are offered only for text within the interactive review limit, so a binary or large file keeps server, device, and keep-both without disabling line choices for other files; insert-both is unavailable for binary files. Files start undecided, and the workbench shows how many are decided and which file still needs a decision. A bulk action may set every file to server or device; it changes the per-file choices, which remain visible and individually adjustable. Directory and mixed directory conflicts remain a single whole-conflict server or device decision, and the workbench states that the choice covers the complete package.

The workbench separates Compare from Result. Compare retains the diff and line-selection controls; Result presents the complete final candidate — every affected document, final path, deletion, additional copy, and directory outcome — rather than removed and retained lines interleaved. The result is derived from the server's resolution candidate computation, not a frontend merge approximation, and binary or large content is shown as an explicit limitation instead of empty text. File deletion stays distinct from an empty file.

Resolution is review-before-apply. Selecting a file choice, choosing lines, or opening Result does not resolve anything; the primary action during editing is **Review result**, available once every file is decided, and only a valid reviewed candidate enables **Apply resolution**, which submits exactly that candidate. Any change to a file choice, line choices, manual text, final path, or deletion invalidates the reviewed candidate and returns the primary action to Review result. A stale package or superseded preview cannot be applied and makes refresh the primary action. Before a consequential submission, the UI states the complete scope of the choice. Conflict resolution uses the authenticated session and CSRF token without password re-entry.

Any future short-window reversal is governed by an accepted RFC and `OBTS-SAF-007`; no UI-only ref reset qualifies as undo.

### OBTS-DASH-STREAM-001: Live Dashboard Invalidation

One owner-session `GET /api/v1/dashboard/events` stream is an invalidation channel, not a second state authority. It uses the same-origin session cookie, rejects unauthorized requests before opening, and sends a fixed `refresh` event on each connection/reconnection so the client fetches its current authorized snapshot. Live `invalidate` events have the closed schema `{account: boolean, vault_ids: string[]}` and include only IDs owned by that stream's account. No durable replay ledger is added; existing per-vault event logs/cursors retain their current behavior. Heartbeats do not trigger refreshes.

Invalidation is published only after durable metadata commit, never from an append-before-persist seam. Notifications cover owner-visible vault/device/status/conflict/activity/settings/diagnostic/deletion changes, excluding session-liveness touches, unchanged status, and unrelated accounts. Bounded subscriber counts, IDs, messages, coalescing, send-time authorization checks, and bounded backpressure are mandatory. Logout, revoke, disable, expiry, dependency loss, abort, socket close, and server shutdown close or fail closed and release subscriptions/timers. Reconnect obtains a fresh authorized snapshot instead of replaying missed invalidations.

## History

History selects a vault path, lists canonical versions and provenance, and presents source or rendered comparison according to file kind. Restore is disabled until a version is selected and clearly states the target. Sensitive plugin bodies remain redacted until an explicit owner action.

Restore advances history; it does not rewrite it.

## Maintenance And Settings

Maintenance presents checklist rows for metadata/database, Git store, temporary workspace, migrations, native Git, permissions, event delivery, and backup contract. Actions explain blocking state and preserve the dashboard/repair surface when one vault is integrity-blocked.

Settings exposes selected-vault Sync controls, consented redacted diagnostics, and account/session actions. Vault-scoped sync controls are unavailable without a selected, accessible vault and remain separate from account controls. Confirmation dialogs state target and consequence. An active authenticated session is not interrupted by username/password re-entry; high-impact destructive intent uses an operation-specific typed phrase.

### OBTS-DASH-DEL-001: Truthful Whole-Vault Deletion Workflow

Settings presents deletion as a server-scope destructive operation using the name and full vault ID in the typed phrase `DELETE <vault_id>`. The dialog states that server Git/history, metadata, transfers/temp material, devices/tokens/connections, and vault diagnostics are deleted, while local client files, independent Bridge state, and existing backups remain untouched. It distinguishes accepted/deleting from completed and never reports content gone from a `202` response.

Pending deletion remains visibly `Deleting` and discoverable after reload/reconnect. Completed vaults leave ordinary selection and may appear only as a minimal recent receipt for 30 days after completion. An unfinished deletion never expires at that receipt deadline. Receipt expiry means not-found and never recreates or reopens the vault. Status/list results are owner-scoped and expose no retained names, paths, commits, content, credentials, or diagnostics.

## Visual Constraints

Use a strong sans-serif UI stack (`-apple-system`, `BlinkMacSystemFont`, `Segoe UI`, sans-serif) and monospace identifiers, compact 13–14px table/body text, 24px page titles, a 4/8/12/16/24/32px spacing scale, one-pixel panel borders, restrained 8–12px radii, warm off-white/deep-ink/teal light tokens, and a matching dark theme with theme-appropriate primary-button foregrounds. New shell transitions respect reduced-motion preferences; breakpoint changes keep keyboard focus on a visible, non-inert control. Avoid nested card grids, heroes, marketing copy, illustrations, gradients, oversized decorative typography, and color-only status meaning. This visual presentation contract does not change polling cadence, API/protocol behavior, conflict draft preservation, or server-derived convergence truth.
