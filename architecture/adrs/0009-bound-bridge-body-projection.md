# ADR 0009: Bound Bridge Body Projection And Query Hydration

- Status: accepted; core and parent-reported local stack evidence available, embedding implementation and final acceptance outstanding
- Date: 2026-09-05
- Architecture revision: 6

## Context

The Bridge currently has production seams that can hydrate PostgreSQL snapshots and retain raw note bodies, derived search text, or worker-wide body collections. That allocation makes corpus size an implicit process-memory multiplier and creates an unsafe temptation to use stale database text when the ordinary headless vault or PostgreSQL is unavailable. The Bridge must remain an ordinary protected device: its visible filesystem/Git state is the body authority, while PostgreSQL is a rebuildable query/projection store except for retained access/audit history.

The redesign must not replace the body source with PostgreSQL, change REST/MCP response shapes, or promise arbitrary single-file streaming. A supported individual file may still be fully parsed within a configurable per-file read/parse limit. The hard bounds concern input-file bytes, body ownership, normal encoded batches and singleton concurrency, not a cap on corpus size or a numerical RSS guarantee. This revision corrects the new agent-authored draft overclaim; it does not redefine an existing strict 8 MiB universal payload requirement.

## Decision

1. Extend `OBTS-BRG-PROJ-001` and add `OBTS-BRG-BODY-001` and `OBTS-BRG-QUERY-001` as the normative Bridge projection, body-attestation, and bounded-query contracts.
2. Make PostgreSQL startup and request serving metadata/query based: use paginated metadata, policy-derived predicates, graph/Base/search candidates, revisions, OIDs, and cursors; never load a full database snapshot or retain a corpus-sized raw-body/`search_text` process map. Config.yaml/runtime auth remains the sole ACL-policy authority; PostgreSQL stores note metadata and executes predicates derived from the current policy.
3. Keep ordinary visible files and protected Git history as the body source. Foreground requests apply runtime policy before hydration and preserve normal 403/404 caller denial. Principal-independent background projection indexes every supported synced note, including private notes, without a requesting principal. Source-integrity/storage failures are separate projection failures that drain leases, retain the cursor, and fail closed.
4. Keep projection readiness ordering: verified source and complete bounded derived writes precede cursor publication. Read, parse, drift, release, batch, and database failures retain the prior cursor, preserve retained audit history, drain body leases, and fail readiness closed. Caller denial is not a projection failure: it returns the existing 403/404, does not dirty global projection, and never causes 503. No path falls back to all-text RAM or stale PostgreSQL body content.
5. Preserve the current REST/MCP and write semantics. Exact foreground reads continue to use existing revision/filesystem/headless guarantees and SQL authorization before body hydration; background projection has no requesting principal and follows the synced-device source boundary. Externally visible errors and response shapes remain unchanged.
6. Keep the 64 MiB default input-file boundary and finite shared in-flight body ownership. Normal derived writes obey configured row count and encoded-parameter bytes (128 rows / 8 MiB defaults). Flush normal work before an indivisible oversized row; execute it alone under the retained file lease and one shared singleton permit through cleanup, then release before another oversized operation. Do not reject that file or raise normal settings. Parser trees, derived singletons and driver copies require separate costing/measurement; YAML/encoding expansion provides no defensible numerical singleton ceiling or hard RSS bound.
7. Preserve legacy arbitrary-substring/title-weight lexical scoring with a projection-produced normalized lowercase plaintext PostgreSQL index, not token-only ranking or full-corpus filesystem scanning. This is allowed derived query storage, including normalized body-derived text in DB/backups, not raw Markdown or an exact-read source. Raw legacy columns remain purged; responses still require original FS/Git and attestation. Preserve graph/link/backlink completeness: internal pages must not impose a silent 500-result cap. Output metadata is output-proportional; page/rank context candidates before token selection, never retaining all candidate bodies.

## Formal and evidence boundary

`OBTS-FM-003` separates file acquisition/verification from independent required rows with kinds and encoded sizes. Multiple rows per file include oversized metadata and tag/link/block fanout. It checks normal-or-singleton batch shape, shared singleton ownership through cleanup, cancellation/drain, partial commit/restart/replay, and cursor publication only after all required rows and cleanup. Reviewed legacy row-overflow and oversized-starvation behavior are explicit negative controls, alongside mixed oversized batches, omitted-row premature completion and early permit release. Finite symbolic sizes are test fixtures, not a parser expansion factor or TLC-to-RSS proof. The model also retains private-note, denial, drift and audit checks. It does not prove SQL policy/compiler correctness, lexical equivalence, response format/order, parser behavior, physical durability or production conformance.

Stage 1 changes architecture and formal evidence only. Stage 2 must add the repository/query seam, attested filesystem reads, bounded projection/embedding/block workers, production-startup fail-closed behavior, integration/fault tests, unchanged REST/MCP golden tests, and an end-to-end deployment test. The stage-1 FM003 trace map recorded those implementation and test obligations as forthcoming rather than treating snapshot/body-retaining paths as evidence of conformance. The implementation acceptance below supersedes that historical checkpoint.

## Consequences

- Large total vault text is no longer rejected merely because an aggregate in-memory admission cap would be exceeded.
- No corpus-body RAM mirror is allowed. Normal payload/row and input/ownership budgets are hard; per-file parser trees, oversized derived rows and driver copies need separate measurements. Output metadata may scale with explicitly requested results. No hard RSS or numerical singleton-byte ceiling is claimed.
- PostgreSQL outage, body drift, source/storage failure, and projection failure are visible fail-closed conditions, not reasons to retain or reconstruct a full text cache; ordinary foreground caller denial remains 403/404 and does not dirty global projection.
- Existing legacy in-memory fixtures may remain only as explicitly isolated test constructors; they are not deployment fallbacks.
- Operators must migrate the old aggregate text setting to the explicit per-file setting and configure finite body/batch budgets before stage-2 activation.

The 0.1.3 core lane now has executable evidence for normal/singleton row budgeting, lexical migration/parity, complete graph/count outputs, paged context ranking and MCP ownership; see the FM003 trace map for exact checks and remaining limits. ## Embedding-worker preimplementation gate

Add `OBTS-BRG-EMBED-001` and the independent FM003 `OBTSBridgeEmbeddingWorker.tla` companion, retaining revision 6 and crate 0.1.3 in this same unlanded change. This is a model-gap correction before production worker changes: the original `DriftRevision` explicitly excludes already verified bodies and therefore cannot cover a provider-pending source/index race or headless/body lock inversion. Neither its 39 checks nor the independently cleared core lane proves concurrent worker conformance.

The companion first reproduces empty-`StoreInner` starvation and ID-only success/failure corruption. It distinguishes source attestation from current SQL generation, independently changes block hash/epoch, invalidates old vectors on SQL publication, and checks zero matched rows for stale success/failure. A previously attested old result may match the old SQL projection while source indexing catches up; it cannot overwrite a new SQL generation. Reindex/backfill is represented as guarded derived publication, not a replacement for the complete-row/cursor projection model.

Trusted background acquisition shares existing headless/filesystem coordination and the body backend, includes private notes without a caller ACL, and always acquires headless before the global body permit. It releases headless before provider await, retains one input and bounded chunk/payload ownership through use/disposal, and completes SQL-only without reacquiring headless while owning the body. With one slot, reversed acquisition and completion reacquisition each produce an actual TLC deadlock against an API holding headless while waiting for body. Cancellation retains/drains ownership and ignores a late reply; stable current work retries under the documented finite-fault/fair-provider assumptions.

`CompleteSQL` is an atomic model boundary, NOT evidence that a PostgreSQL joined update is serializable. READ COMMITTED parent-note revision checks require a transactional parent-row guard or a target-row source epoch with a coordinated replacement protocol. Exact note/block CAS, matched counts, thin queues, streaming extraction/aggregation, real shared-headless single-slot scheduling and disposal need actual-PG/fake-provider regressions before implementation acceptance. The companion trace map records exact current code seams and forthcoming tests. No new C4 boundary or HTTP operation/schema is introduced, and no parser, HTTP/driver allocation or RSS ceiling is claimed.

### Independent-review correction and embedding schema epoch

Review 9e4558bf cleared the modeled worker semantics but blocked inaccurate trace mappings: inverse-acquisition, provider failure, hash/epoch replacement and cancellation were mapped to configurations that disabled them. These now map to exercised configurations, including a dedicated `InverseHeadless` reachability check; `RejectAttestation` likewise maps to the required failure/drift scenario. TLC generated-successor action coverage is captured for every worker configuration, bound to exact model/configuration SHA-256 digests, and checked both by static validation and against fresh TLC output. An existing check ID or a syntactically present but zero-successor action is not evidence of exercise.

The current SQL generation additionally includes an embedding schema/model epoch for notes AND blocks, independent of raw source revision or embedding dimensions. A same-dimension model change can invalidate stored vectors while an old result/failure SQL statement is still pending, even after the originating process dies. `SchemaReset` advances only the derived embedding epoch and invalidates vector/readiness/retry state; queue tokens capture the expected epoch, and `CompleteSQL` checks it atomically for success and failure. Source attestation remains SHA/OID-based and never requires a filesystem model fingerprint.

Source-revision CAS or a separate global-fingerprint preflight is insufficient. Schema invalidation must update a target-row epoch atomically with invalidation, or use a consistent transactional guarding protocol; the mutation must serialize its epoch check with the reset, including old backend statements. The existing block-parent READ COMMITTED warning remains independently applicable. The expanded 48-check worker matrix adds same-source schema note/block/reindex safety and fair retry, pending-SQL reset reachability, stale success/failure witnesses and ignore-schema negative controls. Revision remains 6 and crate 0.1.3; production implementation and actual-PG paused-statement regressions were still forthcoming at that architecture-only checkpoint.

## Local implementation acceptance

The SQL/filesystem core and both embedding modes are implemented and independently reviewed. Context takes its body lease before its SQL transaction; worker completion/invalidation takes a held global schema `FOR SHARE` guard before parent/target rows, while reset takes schema `FOR UPDATE` before scans and atomically advances the epoch. Regression-first actual-PG tests cleared pool1/body1 inversion and new-note/new-block insertion during reset, including stale success and failure. The worker trace now records `checked-worker` with source/test mappings and a required same-binary synthetic-stack receipt; this is not runtime TLA trace replay.

The final disabled/local-worker stack profiles passed 30/34 checks respectively, including scoped API/MCP, private note/block embeddings, completed queues, 8-to-72-MiB corpus process RSS sampling, pending-write SIGKILL/client-volume restore and cleanup. A separate near-63-MiB component fixture measured capture/chunk/batch/encoded-row counters, not isolated RSS. Exact results and remaining limits are in `docs/bridge-embedding-worker-evidence.md` and its saved reports. Earlier review/implementation-pending language above describes gate history, not missing current worker code. No new version increment, live deployment, power-loss, conflict/soak or universal allocator/RSS claim is introduced.
