# Client state and diagnostic admission assurance

Candidate: plugin 0.5.3, server 0.3.31, architecture revision 23. Source base: `58a94a1dda18ded079ebf4cb4f7368ccb8d3b7e4`. Full automated validation passes: 581 Vitest tests and 249 formal checks. Final implementation re-review and review of the two corrected test oracles found no actionable findings. This is not a deployment or physical-device completion record.

## Scope

Queued upload CAS history no longer ranks primary/backup client observations. Local cursor repair preserves independent server/error metadata, requires evidence for every replaced cursor, and propagates publication failures. Genuine ref-backed backup recovery remains supported. Interrupted-apply notices report the retained bounded failure category; recovery retry admission is unchanged.

Diagnostic identity budgets no longer merge clients sharing a reverse proxy. Automatic/device-manual limits are 60/10 per hour, 90/10 per device day, 900/100 per instance hour, 1800/200 retained per owner and 9000/1000 retained globally, always within the existing total ceilings. Connection-origin reports remain automatic after association backfill. Duplicate and rejected reports do not charge acceptance. Payload-free acceptance history spans the rolling day independently of owner deletion and is seeded before startup completes. Auth is rechecked at queued admission. Client retries coalesce by sanitized signature; failures cool down for one minute and successful reports for fifteen minutes. Manual rejection notices allowlist categories and never display response bodies.

## Limits and delivery gates

The single-process admission ledger cannot reconstruct reports deleted before a later server restart. Saturated legacy total quotas remain enforced until ordinary expiry or explicit owner deletion; no migration deletes reports to create reserved space. Accepted-event quotas do not guarantee bounded queue latency against arbitrary request flooding or establish multi-process coordination.

No new interrupted-apply retry is authorized by this change. An existing blocked device still needs a current sanitized recovery category and evidence-specific classification before a safe transition can be selected. Tests do not prove physical mobile suspension, storage power loss, native editor interactions or recovery of a particular existing enrollment.

Before release, run public staged/history guards, identify the reviewed commit, and obtain delivery approval. Any later implementation change requires renewed validation and review of its affected behavior. Verify installed and running versions, existing enrollment catch-up and acknowledgement, retained local edits, cold restart and two-way edits on both affected device classes. A passing new enrollment is not a substitute for that evidence.
